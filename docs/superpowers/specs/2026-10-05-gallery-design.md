# 갤러리 — 사진 밴드 세 개를 내 사진으로

작성 2026-10-05. **하위 프로젝트 2**의 스펙이다.
하위 프로젝트 1(계정 · 서버 저장 · 짧은 주소)이 끝나 있어야 성립한다.

---

## 1. 무엇을 만드나

청첩장 본문에 박혀 있는 **사진 밴드 세 개**를 제작 페이지에서 바꿀 수 있게 한다.

```
invite.html:526   .band.tall   (캡션 있음)   ← 커버 아래
invite.html:597   .band.wide   (캡션 없음)   ← 오시는 길 위
invite.html:756   .band.wide   (캡션 없음)   ← 방명록 위
```

지금은 `img/a-greens.jpg` 세 장이 마크업에 하드코딩돼 있다.
README 가 「남은 것」에 적어 둔 바로 그 문장을 푼다 —
*"사진 밴드 세 개가 고정이라 제작 페이지에서 바꿀 수 없다."*

**격자 갤러리가 아니다.** 상용 서비스(살롱드레터 · 데어무드)는 6~12장 격자에
라이트박스를 띄우지만, 이 프로젝트는 그 길을 안 간다. 이유는 §9 에 적었다.

## 2. 앞선 결정 중 바뀐 것

2026-09-08 설계에서 갤러리를 먼저 하려다 로그인을 넣기로 하면서 전제가 둘 바뀌었다.

| 그때 | 지금 | 왜 |
|---|---|---|
| 22자 난수 키로 소유 | **`auth.uid()`** | 로그인이 그 일을 더 잘한다 |
| 공개 허용 + 30일 자동 삭제 | **로그인 사용자만, TTL 없음** | 익명 전제가 사라졌다 (§7) |
| 원본 250KB 가정 | **920px WebP q75 ≈ 30KB** | 실측. `storage-cost.md` §6 |

## 3. 저장 구조

Storage 버킷 하나. **공개 읽기, 쓰기는 소유자만.**

```
photos/{invitation_id}/{slot}.webp      slot ∈ 1 · 2 · 3
```

**경로의 첫 칸이 청첩장 id 라는 것이 이 설계의 전부다.** 소유 판정을 Storage 가
따로 들고 있지 않고 `invitations` 테이블에 위임한다. 사용자·사진·청첩장 사이에
새 매핑 테이블이 필요 없다.

```sql
insert into storage.buckets (id, name, public)
values ('photos', 'photos', true);

-- 쓰기는 그 폴더 이름이 '내가 가진 청첩장 id' 일 때만.
create policy "owner writes photos" on storage.objects
for insert to authenticated with check (
  bucket_id = 'photos'
  and (storage.foldername(name))[1] in (
        select id from public.invitations where owner = auth.uid())
  and name ~ '^[A-Za-z0-9]{8}/[123]\.webp$'
);
-- update · delete 도 같은 조건. select 는 public 버킷이라 누구나.
```

경로 정규식이 **파일명을 1·2·3 으로 못박는다.** 폴더당 3장이 구조로 강제되므로
개수 제한을 따로 셀 필요가 없고, 임의 파일명으로 저장소를 채우는 것도 막힌다.

## 4. 청첩장 데이터에 무엇을 담나

URL 은 담지 않는다. **경로가 id 에서 나오므로 복원할 수 있다.**

```json
"ph": [
  { "s": 1, "v": 1762300000, "a": "부케", "c": "여덟 번의 봄을 지나" },
  { "s": 3, "v": 1762300120, "a": "흰 구두" }
]
```

| 키 | 무엇 |
|---|---|
| `s` | 슬롯 1 · 2 · 3 |
| `v` | 캐시 무효화용 타임스탬프. **없으면 사진을 바꿔도 예전 것이 보인다** |
| `a` | 대체 텍스트. 접근성에 필요하고 지금 마크업도 전부 갖고 있다 |
| `c` | 캡션. **슬롯 1 에만 쓴다** (`.band.tall` 만 `figcaption` 을 그린다) |

`v` 가 필요한 이유 — 사진을 교체해도 경로가 같아 브라우저·CDN 캐시가 옛 사진을 준다.
`?v=` 를 붙여 주소를 바꾼다.

### 왜 객체가 아니라 배열인가

`deepMerge` 는 **배열은 통째로 덮고 객체는 병합한다.** `ph` 를 객체로 두면
사용자가 사진을 지웠을 때 기본값이 되살아난다 — 이 프로젝트가 이미 한 번 겪은
버그(「필드를 지울 수 없었다」)와 같은 종류다. `intro` · `tl` · `acc` 가 전부
배열인 것과 같은 이유로 배열로 둔다.

### 기본 데모와 사용자 청첩장을 어떻게 가르나

| 경우 | `ph` | 화면 |
|---|---|---|
| 기본 데모 (파라미터 없음) | **없음** | 마크업의 `img/*.jpg` 세 장 그대로 |
| 사용자 청첩장, 사진 2장 | `[{s:1},{s:3}]` | 1·3 번 밴드만. **2번 밴드는 사라진다** |
| 사용자 청첩장, 사진 0장 | `[]` | 세 밴드 전부 사라진다 |

`make.html` 은 저장할 때 `ph` 를 **빈 배열이라도 항상 담는다.** 그래서
"`ph` 키가 없다 = 기본 데모"가 성립한다.

**빈 슬롯에 기본 사진을 남기지 않는다.** 남의 스톡 사진이 내 청첩장에 섞이는 것이
더 나쁘고, "사진 없이도 성립하는 청첩장"이 이 데모의 전제다. 밴드가 빠져도 화면은
무너지지 않는다 — 이미 `aspect-ratio` 로 자리를 잡고 있고 섹션 사이 여백이 메운다.

## 5. 업로드

### 먼저 저장해야 사진을 올릴 수 있다

경로가 `{invitation_id}/` 라 **청첩장이 서버에 있어야 올릴 자리가 생긴다.**
저장 전에는 사진 탭이 잠기고 「먼저 저장하세요」와 저장 버튼을 보여 준다.

이것은 제약이 아니라 로그인 시점 규칙(스펙 §7-1)과 같은 결이다 —
*로그인은 첫 화면이 아니라 저장하려는 순간에 요구한다.*

### 클라이언트 리사이즈

```
파일 선택
  → createImageBitmap(file, { imageOrientation: 'from-image' })   ← EXIF 회전
  → canvas 긴 변 920px
  → canvas.toBlob('image/webp', 0.75)
  → 300KB 넘으면 거부
  → upload(`${id}/${slot}.webp`, { upsert: true })
```

**920px 인 이유** — 밴드는 최대 460px 폭이고 2배 밀도까지 받는다. 그 이상은 낭비다.
**q75 인 이유** — 리포의 사진 세 장으로 재 보니 원본 대비 62% 줄고 육안 차이가 없다.
근거는 `storage-cost.md` §6.

`imageOrientation: 'from-image'` 가 없으면 **아이폰 세로 사진이 눕는다.**
canvas 는 EXIF 를 안 보기 때문이다. 이 한 줄이 그 버그를 막는다.

300KB 상한은 클라이언트와 Storage 버킷 양쪽에 건다. 클라이언트만 믿지 않는다.

### 교체와 삭제

같은 슬롯에 다시 올리면 `upsert` 로 덮고 `v` 를 갱신한다.
삭제는 Storage 에서 지우고 `ph` 에서 그 항목을 뺀다.

**청첩장을 지울 때 사진은 자동으로 안 지워진다.** Storage 는 DB 의 `on delete cascade`
밖이다. 클라이언트가 청첩장 삭제 전에 사진 셋을 먼저 지운다. 그 사이에 실패하면
고아 파일이 남는데, **받아들인다** — 1건이 90KB 이고 Free 저장이 11,000건치다.
정리 자동화는 값보다 비용이 크다.

## 6. 제작 페이지

탭을 **여덟 번째**로 늘린다. 순서는 계좌 다음, 링크 앞이다.

```
인물 · 예식 · 인사말 · 소개 · 이야기 · 계좌 · 사진 · 링크
```

사진은 선택 항목이고 업로드가 가장 무거운 동작이라 뒤쪽에 둔다.
링크 탭은 늘 마지막이어야 한다 — 거기서 결과를 받아 나간다.

탭이 하나 늘면 `role="tablist"` 의 roving tabindex 와 화살표 이동이 그대로 따라간다
(2026-09-08 에 ARIA 패턴을 맞춰 둔 덕이다). 새로 할 일은 없다.

각 슬롯은 **현재 사진 미리보기 · 바꾸기 · 지우기 · 대체 텍스트**를 갖고,
슬롯 1 만 **캡션** 입력을 더 갖는다.

## 7. TTL 을 걸지 않는다

2026-09-08 에 「30일 자동 삭제」를 정했지만 그 전제는 **익명 업로드**였다.
로그인이 생긴 지금은 오용 방어 수단으로서의 TTL 이 필요 없다.

비용으로 다시 따져도 걸 이유가 없다 — 1건 90KB, Free 저장 1GB 는 **11,000건**이다.
`storage-cost.md` §6 의 결론대로 **병목은 저장이 아니라 이그레스**이고,
TTL 은 이그레스를 전혀 줄이지 않는다. 복잡도만 는다.

계정당 청첩장 20개 상한이 이미 1인당 저장을 1.8MB 로 묶고 있다.

## 8. 알고 받아들이는 것

- **미발행 청첩장의 사진은 URL 로 열린다.** `get_invitation` 은 미발행을 막지만
  Storage 공개 버킷은 안 막는다. 청첩장 id(8자)를 알아야 경로를 만들 수 있어
  실질 위험은 낮다. 발행 전 사진을 비밀로 해야 하는 요구가 생기면
  그때 서명 URL 로 바꾼다 — 지금 그러면 하객 열람에 토큰이 필요해져 손해가 크다.
- **고아 파일**이 남을 수 있다 (§5).
- **첫 밴드는 지연 로딩이 아니다.** 커버 바로 아래라 `loading="lazy"` 가 사실상
  즉시 받는다. 이그레스 계산이 이미 그 전제다.

## 9. 격자 갤러리를 아직 안 하는 이유

README 가 갤러리 문제를 이렇게 정의했다 —
*"사진 밴드 세 개가 고정이라 제작 페이지에서 바꿀 수 없다."*

아쉬운 것은 "격자가 없다"가 아니라 **"내 사진을 못 넣는다"**다. 이 스펙이 그걸 푼다.

격자는 나중에 **순수한 추가**로 올릴 수 있다. 버킷 · 업로드 · 리사이즈 · 소유가
여기서 다 깔리므로 남는 것은 화면 작업과 썸네일뿐이다.
`storage-cost.py` 에 60장 모델을 남겨 둔 이유가 이것이다.
