# 모바일 청첩장 — 사진 없이

> 강태윤 · 윤채원 · 2027.04.17
> **가상 데이터입니다.** 이름, 날짜, 장소, 계좌번호 전부 실재하지 않습니다.

| | 주소 |
|---|---|
| 청첩장 | **https://lian220.github.io/onnit-wedding-invitation/** |
| 제작 페이지 | **https://lian220.github.io/onnit-wedding-invitation/make.html** |

로그인 없이 누구나 열립니다.

[ONNIT](https://onnit.co.kr)의 포트폴리오 데모다.
국내 모바일 청첩장 서비스([살롱드레터](https://salondeletter.com))를 분석한 뒤,
같은 기능을 따라 만드는 대신 **다르게 풀 수 있는 지점**을 찾아 구현했다.

빌드가 없는 단일 HTML 파일이다. 외부 의존은 Google Fonts와 QR 생성 라이브러리뿐이다.

```bash
open index.html          # 청첩장
open make.html           # 제작 페이지 (미리보기 때문에 서버가 필요하다)

python3 -m http.server 8080   # make.html 은 이쪽으로 열어야 미리보기가 뜬다
```

## 두 개의 페이지

| 파일 | 무엇인가 |
|---|---|
| `index.html` | 청첩장 본체. 데이터가 없으면 기본값(강태윤 · 윤채원)으로 그린다 |
| `make.html` | 제작 페이지. **모바일 전용**이다. 일곱 단계 탭으로 나뉘고, 하단 고정 바에서 미리보기와 링크 복사를 한다 |
| `css/tokens.css` | 두 페이지가 함께 쓰는 값. 먹 · 선 · 청자, 터치 영역, safe-area |
| `css/base.css` | 리셋과 전역 규칙, 그리고 두 페이지가 정말 같은 것(`.latin`, `.toast`) |

### 왜 CSS를 뺐나

처음에는 두 파일이 각각 자기 `:root`를 들고 있었다. 그러다 값이 어긋났다.

| | `index.html` | `make.html` |
|---|---|---|
| 먹 | `#16181D` | `#15171C` |
| 선 | `#E4E2DD` | `#E5E6E2` |
| 청자 wash | `#EAF1EF` | `#E8F0EE` |

눈으로 구분되지도 않고 아무도 의도하지 않은 차이였다. 한쪽을 고치면 다른 쪽이 어긋났다.
`tokens.css` 한 벌로 못박았다.

**반대로 공유하지 않은 것도 있다.** 청첩장은 종이(흰 바탕, 라운드 2~3px, Gowun Batang)이고
제작 도구는 앱(회색 바탕 위 흰 카드, 라운드 9~12px, 시스템 폰트)이다. 이 차이는 의도한 것이다.
`.f`와 `.seg`는 양쪽에 같은 이름으로 있지만 구현이 다른 별개 컴포넌트라 합치지 않았다.

두 번째 청첩장 템플릿을 만들 때는 `index.html` 맨 위의 `:root` 블록만 갈아끼우면 된다.
전에는 CSS 421줄을 통째로 복사해야 했고, 복사하는 순간 또 어긋나기 시작했을 것이다.

## 서버 없이 어떻게 저장하나

제작 페이지는 입력값을 JSON으로 묶어 base64url로 인코딩한 뒤 **주소의 `#d=` 뒤에 붙인다.**

```
index.html#d=eyJnIjp7Im4iOiLsnbTrj4TtmIQi...
```

청첩장은 열릴 때 그 값을 읽어 기본값 위에 덮는다. 데이터베이스도 API도 없다.
링크 자체가 청첩장이다.

대가가 있다. **주소에 내용이 그대로 담기므로 길어지고, 내용이 노출된다.**
제작 페이지가 주소 길이를 실시간으로 세어 보여주고, 2,000자를 넘으면 경고한다.
실제 서비스라면 서버에 저장하고 짧은 주소를 내주는 것이 맞다. 화면에도 그렇게 적어 두었다.

`#` 뒤만 바뀌면 브라우저가 새로고침을 하지 않아 미리보기가 멈춘다.
청첩장 쪽에 `hashchange`를 걸어 직접 다시 읽게 했다.

## 제작 페이지

모바일 화면만 상정했다. 데스크톱에서 열어도 같은 폭을 유지한다.

일곱 단계로 나눴다. **인물 · 예식 · 인사말 · 소개 · 이야기 · 계좌 · 링크.**
한 번에 한 화면만 보여 주고, 하단 고정 바에 미리보기와 링크 복사를 둔다.
미리보기는 전체 화면으로 덮는다. 좁은 화면에 폼과 미리보기를 나란히 두면 둘 다 못 쓴다.

모바일에서 신경 쓴 것들:

- 입력창 글자를 16px 이상으로 두어 iOS가 화면을 확대하지 않는다
- 터치 영역을 48px로 잡았다
- 하단 바에 `env(safe-area-inset-bottom)`을 넣어 홈 인디케이터를 피한다
- 관계 선택은 드롭다운 대신 세그먼트로 두어 한 번에 고른다
- 설명 입력창은 내용에 맞춰 늘어난다. 탭이 숨어 있는 동안에는 높이를 잴 수 없어,
  탭이 열릴 때 다시 계산한다
- 미리보기에서는 참석 안내 모달을 띄우지 않는다 (`&nogate=1`)

## 무엇을 바꿀 수 있나

신랑·신부 이름과 혼주, 관계, 연락처, 영문 이름 · 예식 일시 · 처음 만난 날 ·
예식장 이름과 홀과 주소 · 인사말 · **우리 두 사람(문답)** · **우리의 시간(타임라인)** · 계좌 목록.

날짜를 바꾸면 **달력이 그 달로 다시 그려지고** 요일과 오전/오후 표기,
카운트다운, 함께한 날 수가 전부 따라 바뀐다. 예식장 이름은 지도 앱 검색어로도 쓰인다.

인사말은 빈 줄로 문단을 나누고 `*별표*`로 감싸면 그 부분이 강조된다.

## 우리 두 사람

살롱드레터의 **프로필형 소개**를 사진 없이 푼 것이다.

원래 형식은 신랑·신부 각각의 사진 옆에 이름과 소개를 붙인 카드다.
얼굴 사진이 없으면 카드가 비어 허전해진다. 그래서 카드를 버리고
**같은 질문에 대한 두 사람의 답을 좌우로 세웠다.**

```
             우리 두 사람
                 │
      신부       │       신랑
     윤채원      │      강태윤
  ───────────────┼───────────────
     요즘 빠져 있는 것
    유화 그리기   │  자전거로 출근하기
  ───────────────┼───────────────
```

가운데 세로선 하나가 머리글부터 마지막 문항까지 관통한다.
커버의 세로쓰기 이름을 가르는 선과 같은 장치다.
질문은 그 선 위에 놓이므로 바탕색으로 선을 끊는다
(`--sec-bg` 토큰을 참조해 틴트 섹션으로 바뀌어도 따라간다).

왼쪽이 신부, 오른쪽이 신랑이다. 커버가 `row-reverse`로 신랑을 오른쪽에 두므로
같은 순서를 지킨다.

한쪽만 답해도 되고, 그 칸은 비워 둔다. 질문 없이 답만 적어도 된다.
둘 다 비면 그 문항이 빠지고, **문항이 하나도 없으면 섹션째 사라진다.**

### 인터뷰는 섹션이 아니라 문항의 성질이다

살롱드레터는 **프로필형 소개**와 **웨딩 인터뷰**를 두 개의 섹션으로 나눠 둔다.
둘 다 문답이다. 손님 화면에 문답 섹션이 연달아 두 개 나오는 셈이다.

여기서는 섹션을 늘리지 않고 **문항마다 답하는 방식을 고르게 했다.**

| 방식 | 데이터 | 화면 |
|---|---|---|
| 따로 | `{q, g, b}` | 두 열로 선다. 짧은 답에 어울린다 |
| 함께 | `{q, t}` | 두 열을 접고 한 줄로 눕는다. 긴 답에 어울린다 |

`t`가 있으면 함께다. 함께 문항은 가운데 세로선 위를 덮고 지나간다
(`.intro-row.solo`에 바탕색과 `z-index`를 준다).
안 쓰는 쪽 필드는 아예 담지 않아 주소가 그만큼 짧다.

좁은 두 열에서는 한글이 음절 단위로 끊겨 `들어 줍니 / 다`가 된다.
답에만 `word-break:keep-all`을 걸어 띄어쓰기에서만 끊고,
안 끊기는 라틴어는 `base.css`의 `overflow-wrap`이 최후에만 개입한다.

## 왜 사진이 없나

청첩장의 절반은 웨딩 사진이다. 사진이 없으면 대개 스톡 이미지를 채워 넣는데,
그 순간 "가짜 커플의 가짜 청첩장"이 되어 데모의 설득력이 사라진다.

그래서 반대로 갔다. **사진을 빼고도 성립하는 청첩장**을 만들 수 있는지가
이 데모가 증명하려는 것이다. 빈 자리는 한글 세로쓰기와 여백이 메운다.

사진은 결국 세 장만 넣었다. **얼굴이 나오지 않는 컷**으로만 골랐다.
Unsplash License로 상업 이용이 가능한 사진이고, 촬영자는 하단에 적어 두었다.
파일에 base64로 직접 박아 두어 외부 요청이 없다. 세 장을 합쳐 320KB 정도다.

커버의 두 이름은 `writing-mode: vertical-rl`로 세로로 세웠다.
전통 청첩장의 형식이고, 웹에서는 거의 쓰이지 않아 첫 화면이 남는다.
읽기 방향이 오른쪽에서 왼쪽이므로 신랑이 오른쪽에 온다.

## 살롱드레터에 없는 것 셋

분석해 보니 기능은 이미 스무 가지가 넘는다. 개수로는 이길 수 없어서,
**하객 입장에서 아쉬운 지점** 세 개를 골라 넣었다.

| 기능 | 무엇을 푸나 |
|---|---|
| **하객별 맞춤 인사** | `?to=이름`을 붙이면 그 사람에게만 보이는 인사가 커버에 뜬다. 공유 섹션에서 링크를 바로 만들 수 있다. 살롱드레터의 1:1 공유를 한 단계 더 밀었다 |
| **큰 글씨 모드** | 청첩장은 부모님 세대가 가장 많이 본다. 우하단 `가` 버튼으로 전체 배율을 키우고 설정을 기억한다. `--fs` 토큰 하나로 전 요소가 함께 커진다 |
| **예식 당일 화면** | 예식일이 되면 길찾기·연락처 배너가 최상단에 자동으로 뜬다. 달력 버튼으로 아무 날에나 미리 볼 수 있다 |

첫 진입에는 참석 안내가 한 번 뜬다. 이미 응답했거나 "오늘 하루 보지 않기"를 누르면
그날은 다시 뜨지 않는다. 하객 수를 세는 것이 청첩장의 실제 목적 중 하나라서 넣었다.

커버에는 꽃잎이 아주 느리게 떨어진다. 캔버스로 그리고 열다섯 장을 넘기지 않는다.
커버가 화면 밖으로 나가거나 탭이 가려지면 멈춘다.
`prefers-reduced-motion`이 켜져 있으면 아예 그리지 않는다.

## 담은 구성

커버 · 인사말 · 연락하기 · 예식 안내(달력, 실시간 카운트다운) ·
우리 두 사람(문답 2열) · 우리의 시간(타임라인, 함께한 날 수) · 오시는 길(주소 복사, 지도 3종, 교통 아코디언) ·
마음 전하실 곳(계좌 아코디언, 복사) · 참석 여부 · 방명록 · 공유하기(맞춤 링크, QR) · 엔딩

## 데이터를 어떻게 바꾸나

예식 정보는 스크립트 맨 위 상수 두 개에 모여 있다.

```js
var WEDDING  = new Date(2027, 3, 17, 13, 0, 0);  // 예식 일시
var FIRSTMET = new Date(2019, 4, 20, 0, 0, 0);   // 처음 만난 날
```

이름·장소·계좌·타임라인 문구는 마크업에 직접 적혀 있다.
달력은 손으로 짠 표라 다른 달로 바꾸려면 `<tbody>`를 교체해야 한다.

## 저장에 관하여

참석 여부와 방명록은 **브라우저 `localStorage`에만** 저장된다.
서버로 전송되지 않고 다른 사람에게 보이지 않는다. 화면 하단에 그렇게 명시해 두었다.

실제 서비스로 쓰려면 이 두 곳만 갈아 끼우면 된다.
`read()` / `write()` 두 함수와 폼 `submit` 핸들러가 저장 경계 전부다.
Supabase 테이블 두 개로 대체하는 것이 가장 짧은 경로다.

`localStorage`가 막힌 환경(사생활 보호 모드 등)에서도 페이지는 정상 동작한다.
읽기·쓰기를 전부 `try/catch`로 감쌌고, 저장이 실패하면 그 사실을 알린다.

## 디자인

라이트 단일 테마다. 청첩장은 종이의 은유이므로 뷰어의 다크 모드를 따라가지 않고
흰 종이 한 세계로 고정했다. 모든 색을 명시해 어떤 배경에 올려도 무너지지 않는다.

| 항목 | 값 | 어디에 |
|---|---|---|
| 먹 | `#16181D` | `css/tokens.css` |
| 청자 (포인트) | `#2F5D57` | `css/tokens.css` |
| 선 | `#E4E2DD` | `css/tokens.css` |
| 종이 | `#FFFFFF` / `#F7F6F3` | `index.html` (이 청첩장의 테마) |
| 한글 디스플레이 | Gowun Batang | |
| 한글 본문 | Noto Sans KR 300 | |
| 라틴 숫자 | Cormorant Garamond | |

모바일 우선이고 최대 460px다. 데스크톱에서는 종이 한 장이 놓인 것처럼 가운데 정렬된다.
`prefers-reduced-motion`을 존중하고, 모든 조작부에 `aria` 상태를 붙였다.

긴 영문 단어와 URL은 `css/base.css`의 `body{overflow-wrap:break-word}` 한 줄로 처리한다.
전에는 계좌번호 · 방명록 · 링크 세 곳에만 `word-break`가 붙어 있었고 인사말에는 빠져 있었다.
큰 글씨 모드에서 인사말이 12px 넘쳤다. 컴포넌트마다 따로 붙이면 반드시 하나를 빠뜨린다.

## 남은 것

- 방명록·참석 여부를 실제 백엔드로 (Supabase)
- 갤러리. 사진 밴드 세 개가 고정이라 제작 페이지에서 바꿀 수 없다.
  사진을 주소에 담을 수는 없으니, 이건 저장소가 생겨야 풀린다
- 짧은 주소. 기본 데이터만으로도 주소가 2,400자를 넘는다.
  서버에 저장하고 짧은 키를 내주는 것이 정답이다
- 카카오톡 공유 SDK. 지금은 링크 복사와 Web Share API로만 처리한다

남은 셋 중 앞의 셋(백엔드 · 갤러리 · 짧은 주소)은 결국 **저장소 하나**의 문제다.
청첩장은 한 번 올리고 수백 명이 읽는 형태라 비용의 거의 전부가 이그레스에서 나온다.
서울 리전 기준 인터넷 아웃바운드가 S3 $0.126/GB, GCS $0.12/GiB인 반면
Cloudflare R2는 $0이다. 자세한 계산은 `claudedocs/storage-cost.md`에 적어 두었다.
